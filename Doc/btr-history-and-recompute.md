# BTR από το 2013 και ενδιάμεσα παιχνίδια – Πώς το χειριζόμαστε

## 1. Στόχος εγγράφου

Αυτό το κείμενο εξηγεί:

- Πώς μπορούμε να υπολογίσουμε το **BilliardToday Rating (BTR)** χρησιμοποιώντας **ιστορικά αποτελέσματα από το 2013 και μετά**.
- Τι κάνουμε αν αργότερα βρούμε **νέα αποτελέσματα που ανήκουν "στη μέση"** της ιστορίας.
- Γιατί είναι σημαντικό να **κρατάμε τη σωστή χρονική σειρά** στα matches.

Δεν είναι implementation guide σε κώδικα, αλλά **conceptual plan** για το backend / migration.

---

## 2. Βασική ιδέα – Το BTR είναι συνάρτηση ολόκληρης της ιστορίας

Το BTR (όπως και κάθε ELO) δεν εξαρτάται από ένα μόνο παιχνίδι, αλλά από **όλα τα προηγούμενα παιχνίδια** ενός παίκτη, με τη σωστή σειρά.

- Αν αλλάξουμε το παρελθόν (προσθέσουμε ή αφαιρέσουμε ένα παλιό match),
  - τότε *θεωρητικά* πρέπει να αλλάξουμε και το σημερινό BTR.
- Άρα, όταν μιλάμε για **ιστορικό από το 2013**, το σωστό BTR σήμερα είναι αυτό που θα παίρναμε αν:
  1. Ξεκινήσουμε από ένα **αρχικό seed rating** για όλους (π.χ. 1500),
  2. Παίξουμε **όλα τα matches από το 2013 και μετά με χρονική σειρά**,
  3. Ενημερώνουμε το BTR μετά από κάθε match.

Συμπέρασμα:

- Το BTR είναι ουσιαστικά το **τελικό αποτέλεσμα** ενός replay όλων των matches από το 2013.
- Αν αργότερα βρούμε ένα match του 2015 που δεν υπήρχε, το BTR που είχαμε υπολογίσει χωρίς αυτό **δεν είναι πια απολύτως σωστό**.

---

## 3. Προτεινόμενη στρατηγική – Full recompute όταν αλλάζει το ιστορικό

Όποτε προσθέτουμε ή τροποποιούμε παλιά αποτελέσματα (μετά το 2013), η πιο καθαρή λύση είναι:

1. **Συλλέγουμε όλα τα matches** που μετράνε για BTR (από το 2013 και μετά).
2. **Ταξινομούμε** τα matches ανά ημερομηνία/ώρα (και δεύτερο κλειδί το match ID αν χρειάζεται).
3. **Μηδενίζουμε** ή επαναφέρουμε τα BTR των παικτών σε ένα κοινό start rating, π.χ. `1500`.
4. **Κάνουμε replay** όλα τα matches με τη σειρά:
   - για κάθε match, υπολογίζουμε το ELO update (σύμφωνα με τους κανόνες BTR),
   - ενημερώνουμε το BTR των δύο παικτών.
5. Στο τέλος γράφουμε το **τελικό BTR** σε κάθε παίκτη.

Με αυτόν τον τρόπο:

- Αν βρίσκουμε **ενδιάμεσα παιχνίδια** (π.χ. παλιό φύλλο αγώνα του 2016),
  - απλά το προσθέτουμε στη βάση με τη σωστή ημερομηνία,
  - και την επόμενη φορά που τρέχει το full recompute, το match μπαίνει στην **σωστή θέση** του.

Δεν μας νοιάζει αν το βρήκαμε σήμερα ή χθες – αρκεί να έχει τη σωστή `match_date`.

---

## 4. Τι κάνουμε όταν βρούμε ενδιάμεσα παιχνίδια (βήμα-βήμα)

Έστω ότι έχουμε ήδη τρέξει ένα full migration για 2013–2024 και έχουμε σημερινά BTR.

Τώρα βρίσκουμε **νέα παλιά αποτελέσματα** (π.χ. από το 2015).

Προτεινόμενα βήματα:

1. **Εισαγωγή νέων αγώνων**
   - Περνάμε τα νέα matches στο σύστημα (μέσω import ή χειροκίνητα),
   - βάζουμε **σωστή ημερομηνία** (π.χ. 2015‑03‑10) και τα κανονικά τους στοιχεία.
2. **Mark για recompute**
   - Μπορούμε να έχουμε μια σημαία/trigger (π.χ. `needs_btr_recompute = true`) σε επίπεδο συστήματος.
3. **Τρέχουμε το BTR recompute job** (offline script / cron):
   1. Παίρνει όλα τα matches από 2013 και μετά,
   2. Τα βάζει σε χρονική σειρά,
   3. Μηδενίζει/επανεκκινεί τα BTR (π.χ. 1500 ή κάποιο seed),
   4. Κάνει replay και στο τέλος γράφει τα νέα BTR.
4. **Ενημέρωση timestamp**
   - Γράφουμε π.χ. `btr_last_calculated_at` σε κάθε παίκτη,
   - ώστε να ξέρουμε πότε έγινε το τελευταίο πλήρες recompute.

Έτσι διασφαλίζουμε ότι:

- Όλα τα παλιά και τα νέα αποτελέσματα είναι **συνεπή** με το τρέχον BTR.
- Δεν χρειάζεται να κάνουμε “μαγικά” με το να βάλουμε ένα παλιό match "στο τέλος".

---

## 5. Θέμα απόδοσης – Πότε είναι ρεαλιστικό το full recompute

Το full recompute είναι πρακτικό όταν:

- ο συνολικός αριθμός matches δεν είναι εκατομμύρια,
- το job τρέχει offline (cron, χειροκίνητο script) και όχι σε real‑time request.

Για έναν τυπικό όγκο δεδομένων μπιλιάρδου από 2013 (λίγες δεκάδες χιλιάδες αγώνες):

- Ένα σωστά γραμμένο script σε Node/TS ή Python μπορεί να κάνει full replay σε **δευτερόλεπτα ή λίγα λεπτά**.

Άρα είναι ρεαλιστικό να πούμε:

- **Κάθε φορά που αλλάζει το ιστορικό**, τρέχουμε full recompute.
- Ή, πιο συντηρητικά, το τρέχουμε π.χ. **μία φορά τη μέρα τη νύχτα**, αν υπάρχουν pending αλλαγές.

---

## 6. "Κλείδωμα" παλιών περιόδων (προχωρημένη στρατηγική)

Αν το ιστορικό μεγαλώσει πολύ ή δεν θέλουμε να μετακινούνται συνεχώς τα BTR κάθε φορά που βρίσκουμε ένα παλιό match, μπορούμε να εφαρμόσουμε στρατηγική **κλειδωμένων περιόδων**.

Ιδέα:

1. Ορίζουμε ότι μέχρι μια ημερομηνία (π.χ. **2018‑12‑31**) το ιστορικό θεωρείται **"παγωμένο"**.
2. Κάνουμε ένα **full recompute μέχρι εκείνη τη μέρα** και αποθηκεύουμε το BTR των παικτών ως **seed** για μετά:
   - π.χ. `btr_seed_2018`.
3. Για matches από 2019 και μετά:
   - χρησιμοποιούμε το `btr_seed_2018` ως αρχικό rating,
   - κάνουμε replay μόνο τα νεότερα matches.

Αν αργότερα βρούμε ένα match του 2014:

- Μπορούμε να επιλέξουμε:
  - είτε **να μην το βάλουμε** στο επίσημο BTR (να είναι μόνο στατιστικό),
  - είτε να πούμε ότι θα γίνει ένα **μεγάλο recompute μέχρι 2018** ξανά και θα ξαναγράψουμε τα seeds.

Αυτό είναι πιο σύνθετο και συνήθως χρειάζεται μόνο:

- αν ο όγκος των matches είναι πολύ μεγάλος, ή
- αν θέλουμε να "παγώσουμε" ιστορικές σεζόν ώστε να μην αλλάζουν συνεχώς τα παλιά ranks.

## 7. Migration από 2013 – Προτεινόμενη ροή

Μια πρακτική ροή για να ενεργοποιηθεί το BTR από το 2013 στο BilliardToday:

1. **Προσθήκη πεδίων στον παίκτη (bt-players)**
   - `btr_overall` (decimal) – το σημερινό συνολικό BTR.
   - `btr_last_calculated_at` (datetime) – πότε έγινε το τελευταίο full recompute.
   - (προαιρετικό) `btr_initial_seed` (decimal) – αν θέλουμε custom αρχικό rating για ορισμένους παίκτες.

2. **Ορισμός κανόνων για το ποιες διοργανώσεις γράφουν BTR**
   - π.χ. μόνο **επίσημα events** με συγκεκριμένο flag,
   - μόνο συγκεκριμένα game types.

3. **Import ιστορικών αποτελεσμάτων από 2013 και μετά**
   - Μέσω CSV ή άλλου migration script,
   - με σωστές ημερομηνίες `match_date`.

4. **Full BTR recompute job** (offline script)
   - Παίρνει όλα τα matches που μετράνε για BTR,
   - Ταξινομεί χρονικά,
   - Θέτει αρχικό BTR (π.χ. 1500 ή `btr_initial_seed`),
   - Κάνει replay όλων των matches,
   - Στο τέλος ενημερώνει `btr_overall` για κάθε παίκτη.

5. **Επαναληπτική χρήση**
   - Όταν προστεθούν νέα παλιά αποτελέσματα ή αλλάξουν ημερομηνίες:
     - τρέχουμε ξανά το job,
     - ή το προγραμματίζουμε να τρέχει περιοδικά (π.χ. nightly) αν υπάρχουν εκκρεμείς αλλαγές.

## 8. Τι σημαίνει αυτό για τα views ανά 1/2/3/5 χρόνια

Έχοντας ένα συνεπές ιστορικό από 2013 και μετά:

- Μπορούμε να χτίσουμε επιπλέον views όπου **ξανατρέχουμε ELO μόνο σε συγκεκριμένο χρονικό παράθυρο** (π.χ. τελευταία 3 χρόνια),
- ή να διατηρούμε προϋπολογισμένα στατιστικά (π.χ. `bt-player-btr-stats`) για `overall`, `last_1y`, `last_3y`, `last_5y`.

Κλειδί όμως είναι ότι η βάση μας έχει **πλήρη και σωστά χρονολογημένο ιστορικό** από το 2013, και ότι όποτε προσθέτουμε ενδιάμεσα παιχνίδια, **το BTR recompute job τα βάζει στη σωστή θέση**.

## 9. Προτεινόμενο Strapi schema για BTR

### 9.1 Νέα/επεκτεινόμενα πεδία στο `bt-players`

Ελάχιστα που χρειάζονται:

- `btr_overall` (decimal)
  - Τρέχον συνολικό BTR (lifetime από 2013 και μετά).
- `btr_last_calculated_at` (datetime)
  - Timestamp τελευταίου full recompute.

Προαιρετικά/χρήσιμα:

- `btr_initial_seed` (decimal, nullable)
  - Custom αρχικό rating για παίκτες με ειδική μεταχείριση (π.χ. πολύ γνωστοί πριν το 2013).
- `btr_notes` (text, nullable)
  - Εσωτερικές σημειώσεις (π.χ. «seed από παλιά εθνική λίστα 2012»).

### 9.2 Flag σε events / matches για το αν γράφουν BTR

Για να μην μπαίνουν όλα τα αποτελέσματα στο BTR:

- Στο επίπεδο **event** (π.χ. `bt-events`):
  - `is_btr_rated` (boolean)
    - Αν είναι `true`, τα matches του event μπορούν να επηρεάσουν BTR.

ή/και:

- Στο επίπεδο **match** (π.χ. `bt-matches`):
  - `is_btr_rated` (boolean)
    - Χρήσιμο αν θέλουμε να εξαιρέσουμε συγκεκριμένα ματς (π.χ. φιλικά).

### 9.3 Πίνακας στατιστικών BTR ανά περίοδο – `bt-player-btr-stats`

Προαιρετικό αλλά δυνατό foundation για views 1/2/3/5 χρόνια.

Προτεινόμενα fields:

- `player` (relation → `bt-players`)
- `game_type` (string/enum)
  - π.χ. `three-cushion`, `balkline-47-1`, κ.λπ.
- `period` (enum)
  - `overall`, `last_1y`, `last_2y`, `last_3y`, `last_5y`.
- `as_of_date` (date)
  - Για ποια ημερομηνία ισχύει αυτό το BTR.
- `btr_value` (decimal)
  - BTR στο συγκεκριμένο period/as_of_date.

Αυτός ο πίνακας δεν είναι απαραίτητος για το πρώτο βήμα (migration από 2013), αλλά βοηθάει αργότερα για γρήγορα rankings και ιστορικά γραφήματα ανά περίοδο.

## 10. Outline για το BTR recompute job (pseudo-code)

Παρακάτω ένα αφαιρετικό παράδειγμα σε pseudo‑code/TypeScript-style για το πώς θα μπορούσε να είναι το offline job που κάνει full recompute του BTR:

```ts
type PlayerId = string

interface Match {
  id: string
  date: Date
  playerA: PlayerId
  playerB: PlayerId
  scoreA: number
  scoreB: number
  gameType: string
  isBtrRated: boolean
}

async function recomputeBtr(fromDate: Date = new Date('2013-01-01')) {
  // 1. Φέρνουμε όλους τους παίκτες
  const players = await loadAllPlayers()

  // 2. Φέρνουμε όλα τα matches που μετράνε για BTR
  const matches = await loadMatches({
    fromDate,
    isBtrRated: true,
  })

  // 3. Ταξινόμηση ανά ημερομηνία (και id για σταθερότητα)
  matches.sort((m1, m2) => {
    if (m1.date.getTime() !== m2.date.getTime()) {
      return m1.date.getTime() - m2.date.getTime()
    }
    return m1.id.localeCompare(m2.id)
  })

  // 4. Αρχικοποίηση BTR για κάθε παίκτη
  const rating: Record<PlayerId, number> = {}

  for (const p of players) {
    rating[p.id] = p.btr_initial_seed ?? 1500
  }

  // 5. Replay όλων των matches με τους κανόνες BTR
  for (const match of matches) {
    const a = match.playerA
    const b = match.playerB

    const rA = rating[a]
    const rB = rating[b]

    // 5.1 Υπολογισμός expected scores
    const expectedA = 1 / (1 + Math.pow(10, (rB - rA) / 400))
    const expectedB = 1 - expectedA

    // 5.2 Πραγματικό σκορ (S_A, S_B) με βάση το αποτέλεσμα
    const { sA, sB } = getActualScores(match) // 1, 0.5, 0 κ.λπ.

    // 5.3 Υπολογισμός K (ή K_eff) με βάση τους BTR κανόνες
    const kA = getKForPlayer(a, rA, match)
    const kB = getKForPlayer(b, rB, match)

    // 5.4 BTR updates
    rating[a] = rA + kA * (sA - expectedA)
    rating[b] = rB + kB * (sB - expectedB)
  }

  // 6. Save back στο Strapi (ή στη βάση)
  const now = new Date()
  for (const p of players) {
    await savePlayerBtr(p.id, {
      btr_overall: rating[p.id],
      btr_last_calculated_at: now,
    })
  }
}

Σημειώσεις:

- Η `getActualScores` υλοποιεί τον γενικό κανόνα ELO (1 / 0.5 / 0 ή άλλα weights αν αποφασίσουμε κάτι ειδικό για multi‑set matches).
- Η `getKForPlayer` ενσωματώνει τη λογική BTR:
  - διαφορετικό K για νέους / παλιούς,
  - προαιρετικά adjustments από AVG / High Run όπως ορίζονται στο `elo-rating-billiards.md`.
- Το παραπάνω είναι **outline**, όχι production κώδικας – σκοπός είναι να φαίνεται η ροή:
  - load → sort → init ratings → replay → save.

Με αυτό ως βάση, μπορούμε εύκολα να φτιάξουμε:

- Cron job (π.χ. 1 φορά τη μέρα αν υπάρχουν αλλαγές ιστορικού),
- Admin κουμπί "Recompute BTR from 2013" στο BilliardToday Admin,
- Στο μέλλον, παραλλαγές που κάνουν replay μόνο για συγκεκριμένο χρονικό παράθυρο (π.χ. τελευταία 3 χρόνια) και γράφουν αποτελέσματα στο `bt-player-btr-stats`.
