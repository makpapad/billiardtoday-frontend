# AI Server Security Agent MVP

Date: 2026-03-17
Target: Linux servers with Plesk, Node, PHP, WordPress, systemd, cron
Goal: fast detection, triage, and safe containment of compromise indicators without giving an LLM unrestricted shell control

## Objective

Build an AI-assisted security agent that can:
- detect persistence and sabotage quickly
- correlate filesystem, process, network, and service anomalies
- generate incident reports automatically
- perform a small set of approved containment actions safely

It should not be a general autonomous root shell.

## Design Principles

- Read-only by default
- Least privilege everywhere
- Deterministic wrappers around system actions
- Narrow remediation allowlist
- Full audit logging of every observation and action
- Human approval for destructive or risky actions
- Local-first evidence collection
- LLM used for analysis and summarization, not unrestricted execution

## High-Level Architecture

The system has 5 layers:

1. Collectors
- gather facts from the host
- run on timer and optionally on event triggers

2. Normalizer
- converts raw outputs into structured JSON events
- removes noise and sensitive data where possible

3. Detection Engine
- rules and heuristics catch obvious malicious patterns
- produces findings with severity and confidence

4. AI Analyzer
- reads structured findings and selected evidence
- builds incident timeline, hypotheses, and recommended actions

5. Response Engine
- executes only pre-approved wrapper actions
- all actions logged and reversible where possible

## Core Components

### 1. Collector Agent

Runs periodically, for example every 5 minutes.

Collects:
- `ps`, `/proc`, deleted-running executables
- `ss`, listeners, established outbound connections
- `systemctl`, `journalctl`, failed units, masked units
- `/etc/systemd/system`, `/run/systemd/system`
- `/etc/cron*`, `/var/spool/cron/crontabs`
- `/etc/udev/rules.d`
- root dotfiles and sensitive service binaries
- auth events and SSH events
- Plesk panel logs and extension/task state
- web access/error logs for suspicious endpoints
- file metadata changes in critical paths
- package ownership for modified binaries

Outputs:
- newline-delimited JSON
- one event per fact
- event types such as:
  - `process.deleted_exe`
  - `service.masked_runtime`
  - `file.permission_anomaly`
  - `cron.suspicious_entry`
  - `udev.suspicious_rule`
  - `network.unexpected_outbound`
  - `web.suspicious_request`

### 2. Rule Engine

This catches high-signal patterns without AI.

Examples:
- executable running from `/tmp`
- deleted executable still running
- zero-byte executable in package-owned path
- zero-byte systemd unit
- immutable flag on unexpected critical files
- file in `/etc/cron.d` containing `curl|sh`, `wget|sh`, `base64 -d`
- `udev` rule with `RUN+=`
- world-writable file under `/etc`, `/root`, `/opt/plesk`
- runtime mask of critical services
- package-owned binary modified recently
- root dotfiles modified unexpectedly
- outbound connection to known suspicious patterns or rare external IPs

Output format:
- finding id
- severity
- evidence refs
- confidence
- recommended action class

### 3. AI Analyzer

The LLM does not receive arbitrary full shell access.

It receives:
- structured findings
- selected evidence snippets
- prior baseline
- host role metadata

It returns:
- summary
- likely timeline
- attack hypothesis
- impact estimate
- recommended next actions
- whether human approval is required

Best use cases:
- correlate multiple weak signals
- distinguish outage from compromise
- write incident report
- prioritize remediation

### 4. Response Engine

This is a strict wrapper layer.

Allowed actions for MVP:
- stop a specific service from an allowlist
- remove a specific known-malicious file path
- quarantine a file into incident folder
- fix permissions on specific critical directories
- unmask and restart a specific allowlisted service
- collect forensic copies and hashes
- reload `sshd`, `systemd`, `udev`
- add temporary firewall block for a specific IP

Not allowed in MVP:
- arbitrary shell execution generated by LLM
- package uninstall without approval
- deleting webroot files automatically
- changing application config automatically
- changing DB contents automatically
- rebooting the host automatically

### 5. Incident Reporter

Generates:
- markdown incident report
- rotation checklist
- timeline
- affected services
- actions taken
- remaining risk

Stores reports locally and optionally sends to Slack/email/Telegram.

## Security Model

### Separation of Privileges

Use three identities:

1. `collector`
- read-only access to logs, metadata, service state
- no write rights

2. `responder`
- only allowed to run a small set of wrappers via `sudo`
- no full shell

3. `operator`
- human
- approves risky actions

### Sudo Model

`sudoers` should allow only wrapper scripts, for example:
- `/usr/local/security-agent/bin/quarantine-file`
- `/usr/local/security-agent/bin/fix-cron-perms`
- `/usr/local/security-agent/bin/unmask-service`
- `/usr/local/security-agent/bin/restart-allowlisted-service`
- `/usr/local/security-agent/bin/block-ip`

No wildcard shell access.

### Prompt Safety

Treat logs and file contents as hostile input.

Defenses:
- pass structured fields instead of raw giant logs
- strip ANSI/control chars
- truncate aggressively
- never let model output become shell directly
- require schema-validated action proposals

## Suggested MVP Stack

### Option A: Python

Good for fast implementation.

Components:
- Python 3.12+
- `systemd` timers
- SQLite or Postgres for findings/history
- `pydantic` for schemas
- `watchdog` or periodic scans
- OpenAI API for analysis/reporting

Why:
- easiest for wrappers, parsers, and JSON pipelines

### Option B: Go

Good if you want a single static binary and low overhead.

Why:
- stronger for daemon-style deployment
- good concurrency
- clean structured tooling

For MVP, Python is faster.

## Detection Coverage for Your Environment

### systemd

Detect:
- zero-byte units
- runtime masks in `/run/systemd/system`
- units created recently in critical windows
- `ExecStart` pointing to `/tmp`, deleted binaries, or unexpected paths
- service binaries replaced or zeroed

### cron

Detect:
- recent changes under `/etc/cron*`
- dangerous perms
- encoded payloads
- fetch-and-exec commands
- orphaned crontabs

### udev

Detect:
- new rules under `/etc/udev/rules.d`
- `RUN+=` rules
- shell invocation inside udev rules

### processes

Detect:
- deleted executables still running
- executables under `/tmp`, `/var/tmp`, `/dev/shm`
- high CPU unknown processes
- suspicious parent-child chains

### packages and binaries

Detect:
- package-owned executable suddenly zero-byte
- immutable flag on service binaries
- package verification mismatch

### Plesk/WordPress/PHP

Detect:
- new admin users
- extension changes
- suspicious scheduled tasks
- plugin/theme file churn
- wp-config changes
- wp-login bursts and suspicious plugin endpoints

### Node/Strapi

Detect:
- env file changes
- PM2 process loss
- app restart loops
- DB connectivity failures that correlate with sabotage

## Baseline Model

The agent should keep a baseline of:
- expected services
- expected listeners
- expected package-owned critical binaries and hashes or sizes
- expected cron files
- expected shell users
- expected Plesk extensions
- expected SSH keys fingerprints

Then it alerts on drift.

## MVP Workflow

### Step 1. Periodic Scan

Every 5 or 10 minutes:
- collectors gather facts
- rule engine creates findings

### Step 2. Triage

If low severity:
- log only

If medium severity:
- alert human
- generate concise summary

If high severity:
- collect forensic copy
- prepare containment plan
- optionally run pre-approved safe actions

### Step 3. AI Report

The LLM writes:
- what likely happened
- why confidence is high or low
- recommended response

### Step 4. Optional Containment

Examples:
- quarantine malicious cron file
- remove malicious udev rule
- repair permissions
- stop known malicious process

### Step 5. Post-Incident Report

Generate:
- markdown file
- indicators
- secrets to rotate
- rebuild recommendation

## Example Safe Actions

Action allowlist examples:

- `quarantine_file(path)`
  - only for paths matching allowed critical directories

- `kill_process(pid)`
  - only if evidence includes deleted executable or `/tmp` executable

- `fix_cron_permissions()`

- `remove_runtime_mask(service)`
  - only for allowlisted services

- `restart_service(service)`
  - only allowlisted services like:
    - `plesk-php83-fpm`
    - `postgresql@16-main`
    - `pm2-root`

- `copy_forensics(src, dst)`

- `hash_file(path)`

## What Not To Do

- Do not give the model raw root shell access
- Do not auto-delete arbitrary files based on model text alone
- Do not let log content directly drive command generation
- Do not let it rotate secrets automatically in MVP
- Do not market it internally as “fully autonomous security”

## Best First Implementation Choice

For your environment, the best first version is:

- Python agent on each host
- read-only scans every 5 minutes
- rules first, LLM second
- Slack/Telegram + markdown reports
- optional wrappers for:
  - quarantine malicious file
  - fix perms
  - restart allowlisted services

That gets real value quickly without making the system dangerous.
